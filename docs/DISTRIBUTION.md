# 16. Build and Distribution Plan

This section is the authoritative plan for how **CASTALIA DOS** is packaged,
built, verified, and released. It defines every distribution format we ship,
the exact Linux-native tooling used to produce each one, the recommended first
release path, the full version roadmap with per-release contents, the
build-artifact naming and versioning scheme, and the reproducibility and
release checklist.

CASTALIA DOS is a FreeDOS-based, legally-clean DOS-compatible environment for
real retro hardware (386SX first). Everything below assumes that constraint:
FAT12/FAT16 media, real-mode DOS, VGA text-mode tooling, and open/free
components only. No Microsoft code, binaries, manual text, or branding is ever
packaged.

All build tooling runs on a modern **Linux** host. All DOS-side steps that
*must* run under DOS (chiefly `SYS`) are performed inside an emulator with a
FreeDOS environment, and their output (a known-good boot sector) is captured
so subsequent builds are fully scriptable. Every artifact is smoke-tested in
**DOSBox-X** and **86Box** before release; the flagship 386SX Edition is
additionally validated on real 386SX hardware.

## 16.1 Overview of distribution formats

| Format | File | Media | First shipped | Audience |
|---|---|---|---|---|
| Bootable floppy image | `*-floppy.img` | 1.44 MB floppy | 0.1 Almenara | Rescue, quick boot, "try it" |
| Multi-floppy installer set | `*-boot.img` + `*-diskNN.img` | N × 1.44 MB | 0.5 Morella | Real hardware without a CD |
| Hard-drive install ZIP | `*-install.zip` | any DOS filesystem | 0.1 Almenara | Existing DOS/FreeDOS systems |
| ISO image | `*.iso` | CD-ROM | 0.5 Morella (beta) | CD install / live boot |
| CompactFlash card image | `*-cfNNN.img` | CF via dd/imager | 1.0 Tombatossals | Real 386SX/486 with CF-IDE |

The two formats shipped from day one — the single bootable floppy and the
hard-drive install ZIP — are the backbone of the project. The other three are
staged in deliberately (see §16.7, the recommended first release path).

## 16.2 Format: Bootable floppy image (1.44 MB rescue + boot disk)

**Purpose.** A single, self-contained 1.44 MB disk that boots a working
CASTALIA DOS environment: the FreeDOS kernel, FreeCOM shell, the CASTALIA boot
menu (`CLEAN`, `XMS`, `EMS`, `CDROM`, `WIN3X`, `DIAG`, `SAFE`, `PROMPT`), the
core memory managers, and enough Castalia tools to diagnose and rescue a
machine. It doubles as the emergency rescue disk (`SAFE` profile = bare
`KERNEL.SYS` + `COMMAND.COM`, no drivers) and as the "try before you install"
disk.

**Contents (target on a 1.44 MB image):**

| Path on disk | Purpose |
|---|---|
| `KERNEL.SYS` | FreeDOS kernel (GPLv2+) |
| `COMMAND.COM` | FreeCOM shell (GPLv2+) |
| `CONFIG.SYS` | 8-entry boot menu (`MENU` lines + `n?` prefixes) |
| `AUTOEXEC.BAT` | per-profile setup, launches `CASTALIA.EXE` |
| `HIMEMX.EXE`, `JEMM386.EXE` | XMS / EMS managers |
| `CTMOUSE.EXE` | mouse driver (GPL; ship source) |
| `CASTALIA.EXE` | text-mode main menu |
| `MEMPROF.EXE`, `HWINFO.EXE`, `SAFEBOOT.EXE` | profile switch, diagnostics, rescue |

Space on 1.44 MB is tight, so the floppy carries the rescue/diagnostic subset
of Castalia tools, not the full launcher/game database (those live in the
hard-drive install and ISO).

**How to build (Linux).** We create the image, lay down a FAT12 filesystem
with a FreeDOS boot sector, then copy files with `mtools` — no root, no
loop-mount required:

```sh
# 1. Create a blank 1.44 MB image (2880 * 512-byte sectors).
dd if=/dev/zero of=castalia-dos-0.2-peniscola-floppy.img bs=512 count=2880

# 2. Format FAT12 with a *known-good FreeDOS boot sector* (fdboot.bin),
#    a fixed volume label, and a fixed serial for reproducibility.
mformat -f 1440 -v CASTALIA -N 0 \
        -B build/boot/fdboot.bin \
        -i castalia-dos-0.2-peniscola-floppy.img ::

# 3. Copy the boot files first (kernel must be locatable by the VBR),
#    then the rest of the staged tree.
mcopy -i castalia-dos-0.2-peniscola-floppy.img -m -Q \
      build/floppy/KERNEL.SYS build/floppy/COMMAND.COM ::
mcopy -i castalia-dos-0.2-peniscola-floppy.img -m -Q -s \
      build/floppy/CONFIG.SYS build/floppy/AUTOEXEC.BAT \
      build/floppy/*.EXE build/floppy/*.SYS ::
```

- `-N 0` fixes the FAT volume serial number so identical inputs yield
  byte-identical images (reproducibility, §16.10).
- `-m` preserves file modification times; combined with `SOURCE_DATE_EPOCH`
  (see §16.10) the timestamps are deterministic.
- `-B build/boot/fdboot.bin` installs the FreeDOS FAT12 boot record rather
  than the generic mtools one, so the disk actually boots `KERNEL.SYS`.

**Producing `fdboot.bin` (one time, then committed).** The FreeDOS boot sector
is generated by the DOS-side `SYS` command, which must run under DOS. Boot a
FreeDOS install in DOSBox-X or 86Box, `SYS A:` a formatted 1.44 MB disk, then
capture the first sector back on Linux:

```sh
# From the emulator's floppy image after SYS has run:
dd if=synced-floppy.img of=build/boot/fdboot.bin bs=512 count=1
```

`mformat -B` re-patches the BPB fields into this captured sector for the target
geometry, so one `fdboot.bin` serves every floppy build. Alternatively,
`ms-sys -1 -f -w image.img` writes a FreeDOS FAT12 boot record directly from
Linux — kept as a documented fallback if regenerating `fdboot.bin`.

**How to test.**

- **DOSBox-X:** `dosbox-x -conf tests/dosbox-x.conf` with
  `boot castalia-dos-0.2-peniscola-floppy.img`. Confirm the menu appears, each
  profile boots, `MEM /C` shows the expected free conventional memory per
  profile (CLEAN ~615 KB, XMS ~620-631 KB), and `HWINFO.EXE` runs.
- **86Box:** configure a 386SX machine, attach the image as floppy A:, set A:
  as boot device. This is the closer-to-hardware gate; verify real-mode timing,
  the boot menu, and `CTMOUSE` detection.

**Pros.**

- Smallest, fastest artifact; boots on essentially any PC with a floppy drive.
- Doubles as the official rescue disk with zero extra work.
- Trivial to reproduce and checksum; excellent for CI smoke tests.

**Cons.**

- 1.44 MB ceiling: cannot carry the full tool set, help system, or games.
- Floppies are slow and physically unreliable on aging hardware.
- Install-to-hard-disk from a single floppy is limited; that is the ZIP's job.

## 16.3 Format: Multi-floppy installer set (boot disk + N data disks)

**Purpose.** A guided, floppy-only installation for real machines that have no
CD-ROM and no easy way to receive a large ZIP. Disk 1 boots a minimal
environment and launches `SETUP.EXE`; the remaining disks carry the full
component payload, split to fit 1.44 MB each. `SETUP.EXE` prompts for each disk
in turn and installs to `C:` with the standard directory layout
(`C:\DOS`, `C:\CASTALIA\...`).

**Layout of a set:**

| Disk | Label | Contents |
|---|---|---|
| Boot / Disk 1 | `CASTALIA_1` | `KERNEL.SYS`, `COMMAND.COM`, `CONFIG.SYS`, `AUTOEXEC.BAT`, `SETUP.EXE`, memory managers, `CTMOUSE` |
| Disk 2 | `CASTALIA_2` | `C:\DOS` FreeDOS base utilities + `JEMM386`, `KEYB`, `SMARTDRV`, `SETVER` |
| Disk 3 | `CASTALIA_3` | `C:\CASTALIA\BIN` tools, `\DRV` drivers (`UIDE.SYS`, `SHSUCDX`) |
| Disk 4 | `CASTALIA_4` | `C:\CASTALIA\HELP`, `\CFG` (`CASTALIA.INI`, `PROFILES.INI`, `GAMES.INI`) |
| Disk N | `CASTALIA_N` | Overflow / optional components as the tree grows |

The build script packs the staged install tree into 1.44 MB "bins" using a
deterministic bin-packing pass so a given release always produces the same
number of disks with the same file placement.

**How to build (Linux).** Each disk is a floppy image built exactly as in
§16.2; only disk 1 is made bootable (`-B fdboot.bin`), the data disks are plain
FAT12:

```sh
# Boot disk (bootable):
mformat -f 1440 -v CASTALIA_1 -N 0 -B build/boot/fdboot.bin \
        -i castalia-dos-0.5-morella-boot.img ::
mcopy -i castalia-dos-0.5-morella-boot.img -m -Q -s build/set/disk1/. ::

# Data disks (not bootable):
for n in 01 02 03; do
  img="castalia-dos-0.5-morella-disk${n}.img"
  dd if=/dev/zero of="$img" bs=512 count=2880
  mformat -f 1440 -v "CASTALIA_${n}" -N 0 -i "$img" ::
  mcopy -i "$img" -m -Q -s "build/set/disk${n#0}/." ::
done
```

**How to test.**

- **DOSBox-X:** boot disk 1, run through `SETUP.EXE`, and swap data disks using
  the built-in disk-swap (`Ctrl-F4` to cycle mounted images, or scripted
  `imgmount`/`boot -l a`). Confirm a completed install boots from `C:`.
- **86Box:** the realistic gate — a single floppy drive forces genuine disk
  swapping; verify `SETUP.EXE` prompts and resumes correctly across swaps and
  that the installed system boots the full 8-entry menu.

**Pros.**

- Installs on hardware with only a floppy drive — a real 386SX use case.
- Familiar, period-correct experience; robust component selection in `SETUP`.

**Cons.**

- Tedious for the user (multiple physical swaps) and the most failure-prone
  medium (any bad floppy aborts the install).
- Highest build and QA cost per release: bin-packing, per-disk labels,
  swap-flow testing. This is why it is deferred to 0.5 (see §16.7).

## 16.4 Format: Hard-drive install ZIP (unzip on DOS/FreeDOS, run SETUP)

**Purpose.** The primary installation path for anyone who already has a working
DOS or FreeDOS system (or a CF card prepared elsewhere). The user copies the
ZIP to the machine, unzips it, and runs `SETUP.EXE`. `SETUP` writes the
CASTALIA directory tree, installs `CONFIG.SYS`/`AUTOEXEC.BAT` (backing up any
existing ones to `C:\CASTALIA\BACKUP`), and optionally makes `C:` bootable.

**Contents of the ZIP:**

```
castalia-dos-0.2-peniscola-install.zip
├── SETUP.EXE                 Castalia installer (text-mode)
├── SETUP.INI                 install manifest (files, targets, profiles)
├── PACKAGE/                  staged payload, mirrors installed layout
│   ├── DOS/                  FreeDOS base utils + memory managers
│   ├── CASTALIA/BIN/         CASTALIA.EXE, LAUNCH.EXE, MEMPROF.EXE, ...
│   ├── CASTALIA/DRV/         UIDE.SYS, SHSUCDX, ...
│   ├── CASTALIA/CFG/         CASTALIA.INI, PROFILES.INI, GAMES.INI
│   └── CASTALIA/HELP/        help text pages
├── LICENSES/                 all license texts (MIT, GPLv2, BSD, CC BY 4.0)
├── MANIFEST.txt              per-file license + source attribution
└── README.TXT                short install instructions (8.3, CRLF)
```

**How to build (Linux).** The ZIP must be readable by DOS unzip tools
(`INFO-ZIP UNZIP`), so we use plain deflate, 8.3-friendly names inside
`PACKAGE/`, and no Unix mode/UID metadata that could confuse DOS tools:

```sh
cd build/install
# -X drops extra file attributes; -r recurse; sorted input for reproducibility.
find . -type f | LC_ALL=C sort > ../filelist.txt
zip -X -9 ../../dist/castalia-dos-0.2-peniscola-install.zip -@ < ../filelist.txt
```

`README.TXT` and any DOS-facing text are written with CRLF line endings; the
repo `.gitattributes` normalizes source to LF, so the build step converts
DOS-facing text explicitly (`unix2dos` or an equivalent filter) before zipping.

**How to test.**

- **DOSBox-X:** mount a blank FAT16 hard-disk image as `C:`, mount the ZIP's
  host directory as `D:`, `UNZIP` it, run `SETUP.EXE`, reboot from `C:`, verify
  the menu and tools. Also verify the `C:\CASTALIA\BACKUP` step preserves a
  pre-existing `CONFIG.SYS`.
- **86Box:** install onto a real IDE hard-disk image on a 386SX profile; verify
  `SYS`/boot-sector install path and that all profiles come up.

**Pros.**

- No physical media; the easiest, most reliable install path.
- Full payload with no size split; carries the complete tool set and help.
- Works today on any existing DOS/FreeDOS box — ideal for early adopters.

**Cons.**

- Requires an *already-working* DOS system and an `UNZIP` tool to bootstrap.
- Does not itself make bare metal bootable; pair it with the boot floppy for a
  from-scratch install.

## 16.5 Format: ISO image (later — CD-based install / live)

**Purpose.** A single bootable CD-ROM that both installs CASTALIA DOS and can
run "live" for demos and rescue. It bundles the full payload plus optional
extras too large for floppies. Uses El Torito floppy-emulation boot: the CD
boots the very same 1.44 MB boot floppy image (§16.2), which then finds the
CD's `SHSUCDX`/`UIDE` drivers and `SETUP`.

**Staging tree for the ISO:**

```
iso/
├── CASTALIA.IMG          El Torito boot image (= the 1.44 MB boot floppy)
├── SETUP.EXE
├── PACKAGE/              full install payload (as in the ZIP)
├── LICENSES/
├── MANIFEST.TXT
└── README.TXT
```

**How to build (Linux).** With `xorriso` (preferred) or `genisoimage`; ISO 9660
Level 2 with Joliet off (keep 8.3 names for DOS), floppy-emulation El Torito:

```sh
# Preferred: xorriso in mkisofs-compatibility mode.
xorriso -as mkisofs \
  -V CASTALIA_DOS -iso-level 2 \
  -b CASTALIA.IMG -c BOOT.CAT \
  -o dist/castalia-dos-1.0-tombatossals.iso \
  iso/

# Equivalent with genisoimage (floppy emulation is the default El Torito mode
# when the boot image is a 1.44 MB floppy and -no-emul-boot is omitted):
genisoimage -V CASTALIA_DOS -iso-level 2 \
  -b CASTALIA.IMG -c BOOT.CAT \
  -o dist/castalia-dos-1.0-tombatossals.iso \
  iso/
```

For no-emulation boot (loading `KERNEL.SYS` directly without a floppy image)
add `-no-emul-boot -boot-load-size 4`; floppy emulation is preferred because it
reuses the already-tested boot floppy verbatim.

**How to test.**

- **DOSBox-X:** `imgmount D iso.iso -t iso` and `boot -l d` (or attach as a
  bootable CD). Confirm the El Torito boot floppy comes up and `SETUP` sees the
  CD drive via `SHSUCDX`.
- **86Box:** attach an ATAPI CD-ROM to a 486/early-Pentium profile (386SX often
  lacks a practical CD path), set CD as boot device, verify live boot and
  install-to-HDD.

**Pros.**

- One artifact carries everything; no disk swapping; fast install.
- Live/rescue mode; convenient for demos and for machines with a CD drive.

**Cons.**

- Many target 386SX machines have no CD-ROM, so it is not the primary path.
- El Torito + ATAPI adds real-hardware variability (driver/BIOS quirks) that
  needs its own QA pass — the reason it lands as a beta in 0.5, stable in 1.0.

## 16.6 Format: CompactFlash card image (later — dd / win32-imager to CF)

**Purpose.** A ready-to-run whole-disk image for real 386SX/486 machines that
use a CF-to-IDE adapter as their hard disk. The user writes the image to a CF
card with `dd` (Linux/macOS) or a GUI imager (Win32 Disk Imager, Rufus in DD
mode), inserts the CF, and boots directly into an installed CASTALIA DOS. No
install step required — it is a pre-installed system on a partitioned image.

**Structure of the image (a full disk, not a filesystem):**

```
castalia-dos-1.0-tombatossals-cf256.img   (~256 MB whole-disk image)
├── MBR                      FreeDOS master boot record (boots active part.)
└── Partition 1 (FAT16)      active, bootable
    ├── KERNEL.SYS, COMMAND.COM, CONFIG.SYS, AUTOEXEC.BAT
    ├── DOS\                  FreeDOS base + memory managers
    └── CASTALIA\             full tool set, CFG, HELP, GAMES
```

**How to build (Linux).** Build a partitioned whole-disk image with a FreeDOS
MBR and a bootable FAT16 partition, populate it with `mtools`, then it is ready
to `dd`:

```sh
SIZE_MB=256
IMG=dist/castalia-dos-1.0-tombatossals-cf256.img

# 1. Blank whole-disk image.
dd if=/dev/zero of="$IMG" bs=1M count=$SIZE_MB

# 2. One primary FAT16 partition (type 0x06), marked active/bootable.
#    Start at sector 63 for period-typical CHS-friendly alignment.
sfdisk "$IMG" <<'EOF'
label: dos
unit: sectors
start=63, type=06, bootable
EOF

# 3. Write a FreeDOS MBR (boot code that chains the active partition).
ms-sys -m "$IMG"            # or dd a captured FreeDOS MBR: mbr.bin

# 4. Format + populate the partition via an mtools offset drive.
#    (mtools ~/.mtoolsrc maps p: to the partition at offset 63*512.)
export MTOOLSRC=build/mtoolsrc-cf256
mformat -F -v CASTALIA -N 0 -B build/boot/fdboot16.bin p:
mcopy -m -Q -s build/install/PACKAGE/. p:
mcopy -m -Q build/install/boot/{KERNEL.SYS,COMMAND.COM,CONFIG.SYS,AUTOEXEC.BAT} p:
```

Where `build/mtoolsrc-cf256` contains, e.g.:

```
drive p: file="dist/castalia-dos-1.0-tombatossals-cf256.img" offset=32256
```

(`32256 = 63 * 512`.) `ms-sys -m` writes the DOS/FreeDOS MBR; `fdboot16.bin` is
the FAT16 partition boot record captured the same way as `fdboot.bin` (§16.2)
but from a `SYS`-ed hard disk. **Writing to a real card** is then just:

```sh
# Linux (double-check the device node!):
sudo dd if=$IMG of=/dev/sdX bs=4M conv=fsync status=progress
# Windows: Win32 Disk Imager / Rufus (DD mode), target the CF reader.
```

**How to test.**

- **86Box:** attach the image as a hard disk on a 386SX profile with the right
  CHS geometry; boot directly. This is the authoritative test because CF-IDE
  geometry and BIOS translation (LBA vs CHS) are exactly what breaks on real
  hardware.
- **DOSBox-X:** `imgmount 2 img -size 512,63,H,C -t hdd` then `boot -l c` for a
  quick sanity boot; DOSBox-X is less faithful to CHS quirks, so 86Box is the
  gate.

**Pros.**

- Zero-install, boot-and-go on real hardware; the most convenient real-metal
  format we ship.
- Encodes a known-good geometry and layout, removing user setup mistakes.

**Cons.**

- Geometry sensitivity: CF card size vs BIOS CHS translation must match, or the
  card won't boot — needs careful, hardware-informed QA.
- Fixed image size wastes CF capacity (or must be published in several sizes),
  and whole-disk images are large downloads.
- Requires the user to have a CF writer; overwrites the whole card.

## 16.7 Recommended best first-release path

**Ship two formats first: the single bootable floppy and the hard-drive install
ZIP.** Defer the multi-floppy installer polish and the ISO/CF images to later
releases.

| Release | Formats produced | Deferred |
|---|---|---|
| 0.1 Almenara | bootable floppy, hard-drive ZIP | everything else |
| 0.2 Peñíscola | bootable floppy, hard-drive ZIP | multi-floppy, ISO, CF |
| 0.5 Morella | + multi-floppy set, + ISO (beta) | CF |
| 1.0 Tombatossals | all five formats | — |
| 1.1 Montornés | all five formats | — |

**Why these two first.**

1. **They exercise the whole pipeline with the least tooling risk.** The floppy
   proves boot-sector + kernel + menu; the ZIP proves the full payload +
   `SETUP` + directory layout. Between them they cover "does it boot?" and
   "does it install?" — the two questions a 0.1/0.2 must answer.
2. **They are fully reproducible from Linux** with `dd`, `mtools`, and `zip`
   plus a single committed boot sector. No El Torito, no partition tables, no
   CHS geometry — the parts most likely to consume QA time — are on the
   critical path yet.
3. **They serve the earliest real users.** Retro users overwhelmingly have a
   floppy drive and/or an existing DOS box; the floppy + ZIP combination lets
   someone go from bare metal (boot floppy) to installed system (ZIP) today.
4. **The deferred formats are strictly additive.** The multi-floppy set reuses
   the §16.2 floppy builder plus bin-packing; the ISO reuses the boot floppy as
   its El Torito image and the ZIP payload as its tree; the CF image reuses the
   installed tree. Nothing about shipping them later forces rework of 0.1/0.2 —
   they layer on top once the core is proven and hardware-tested.

The cost we are deferring is real: multi-floppy swap-flow QA, El Torito/ATAPI
variability, and CF geometry sensitivity each need their own hardware-informed
test pass. Front-loading them would slow the first release without improving
the core product. So 0.1 and 0.2 stay lean, and 0.5/1.0 add media breadth once
the foundation is trustworthy.

## 16.8 Full version plan

Codenames are Valencian/Castellón fortress towns. Each release below lists its
theme/goal, the components and tools it ships, the distribution formats it
produces, and what is **explicitly not yet included**.

### CASTALIA DOS 0.1 "Almenara"

**Theme / goal.** *It boots, and it is ours.* First public proof: a genuine
FreeDOS-based boot with Castalia branding, the canonical boot menu, and a
minimal-but-real install path. Correctness over breadth.

**Included components / tools.**

| Item | Notes |
|---|---|
| FreeDOS `KERNEL.SYS`, `COMMAND.COM` | GPLv2+, in `third_party/`, source kept |
| `CONFIG.SYS` 8-entry menu | All labels present; `CLEAN`, `XMS`, `SAFE`, `PROMPT` fully wired |
| `HIMEMX.EXE` | XMS for `CLEAN`/`XMS` profiles |
| `CTMOUSE.EXE` | mouse driver present |
| `CASTALIA.EXE` | main menu shell (navigable; launches tools/prompt) |
| `MEMPROF.EXE` | reads current profile, reboots into a chosen one |
| `HWINFO.EXE` | basic CPU/RAM/video/mouse detection (`DIAG` target) |
| `SAFEBOOT.EXE` | rescue helper on the `SAFE` profile |
| `SETUP.EXE` | basic hard-drive installer (copy tree, write boot files) |
| Boot/branding screen | Castilian-fortress palette, calm copy |

**Distribution formats.** Bootable floppy (`-floppy.img`), hard-drive install
ZIP (`-install.zip`).

**Explicitly NOT included.** `JEMM386`/EMS-based profiles (`EMS`, `CDROM`,
`WIN3X`) are stubbed to fall back to `CLEAN`; sound (`SETSOUND`, `SET BLASTER`);
game launcher (`LAUNCH`/`GAMEVAULT`), `GAMECFG`, `CFGEDIT`; CD-ROM drivers
(`UIDE`/`SHSUCDX`); `SMARTDRV`, `KEYB`, `SETVER` integration; help system; game
database; multi-floppy set; ISO; CF image; file manager.

**Theme / goal.** *A real, usable gaming DOS.* The release the project is
actually judged by: all core gaming profiles work, sound is configurable, games
launch from a menu, and the hard-drive install is complete. This is the target
of the best-first-release path (§16.7).

**Included components / tools (adds to 0.1).**

| `KEYB`, `SMARTDRV`, `SETVER` | keyboard layout, disk cache, per-program version |

| `GAMECFG.EXE` | per-game profile/sound overrides |

| Full `CASTALIA.EXE` menu | tools, games, profile switch, help entry points |
| `CASTALIA\CFG` seeded | `CASTALIA.INI`, `PROFILES.INI`, starter `GAMES.INI` |
| `SETUP.EXE` (complete) | backs up existing configs to `C:\CASTALIA\BACKUP` |

**Distribution formats.** Bootable floppy (`-floppy.img`), hard-drive install
ZIP (`-install.zip`).

**Explicitly NOT included.** `WIN3X` profile is experimental/unsupported (marked
as such in the menu); multi-floppy installer set; ISO; CF image; `CASTFM`

real-hardware certification (still emulator-validated).

### CASTALIA DOS 0.5 "Morella"

**Theme / goal.** *Complete installer and media.* Feature-broad beta: a polished
`SETUP` with component selection, floppy-only installation for CD-less
machines, a working Windows 3.x mode, an expanded help system, and the first CD
image.

**Included components / tools (adds to 0.2).**

| Item | Notes |
|---|---|
| `SETUP.EXE` component selection | choose profiles, tools, and games to install |
| Multi-floppy installer set | boot disk + N data disks, deterministic packing |
| `WIN3X` profile supported | `JEMM386` (EMS on) + `SMARTDRV` + mouse for Win 3.1/WfW |

## 16.9 Build-artifact naming, versioning, and `dist/`

**Naming scheme.**

```
castalia-dos-<version>-<codename>-<format>[-<variant>].<ext>
```

- `<version>` — numeric (`0.1`, `0.2`, `0.5`, `1.0`, `1.1`).
- `<codename>` — lowercased, ASCII-folded (no accents) fortress name:
  `almenara`, `peniscola`, `morella`, `tombatossals`, `montornes`.
- `<format>` — one of `floppy`, `boot`, `diskNN`, `install`, `cfNNN`; the ISO
  omits the format token (the `.iso` extension carries it).
- `<variant>` — optional (e.g. CF size is folded into the format token as
  `cf256`).

| Example artifact | What it is |
|---|---|
| `castalia-dos-0.1-almenara-floppy.img` | 1.44 MB bootable floppy |
| `castalia-dos-0.1-almenara-install.zip` | hard-drive install ZIP |
| `castalia-dos-0.2-peniscola-floppy.img` | 0.2 bootable floppy |
| `castalia-dos-0.2-peniscola-install.zip` | 0.2 hard-drive ZIP |
| `castalia-dos-0.5-morella-boot.img` | installer set boot disk |
| `castalia-dos-0.5-morella-disk01.img` | installer set data disk 1 |
| `castalia-dos-0.5-morella.iso` | CD image (beta) |
| `castalia-dos-1.0-tombatossals.iso` | CD image (stable) |
| `castalia-dos-1.0-tombatossals-cf256.img` | 256 MB CF card image |

**Versioning rules.**

- The pair `<version>`+`<codename>` is fixed per release and always travels
  together in filenames and git tags.
- Git tag form: `v<version>-<codename>` (e.g. `v0.2-peniscola`), annotated.
- Pre-release builds append `-rcN` to the version token
  (`castalia-dos-1.0rc1-tombatossals-...`); CI/nightly builds append a short
  commit hash and never land in `dist/` releases.
- `CASTALIA.INI` and `CASTALIA.EXE`'s about box report the same
  `<version> "<codename>"` string, so an installed system is self-identifying.

**Checksums and signatures.**

- Each release directory contains a single `SHA256SUMS` covering every artifact,
  plus a per-artifact `<name>.sha256` for convenience.
- `SHA256SUMS` is verifiable with `sha256sum -c SHA256SUMS`.
- Optionally, `SHA256SUMS.asc` is a detached GPG signature from the project
  release key so users can verify authenticity, not just integrity.

**Contents of `dist/`** (one subdirectory per release, mirrored to the GitHub
release assets):

```
dist/
└── 0.2-peniscola/
    ├── castalia-dos-0.2-peniscola-floppy.img
    ├── castalia-dos-0.2-peniscola-floppy.img.sha256
    ├── castalia-dos-0.2-peniscola-install.zip
    ├── castalia-dos-0.2-peniscola-install.zip.sha256
    ├── SHA256SUMS
    ├── SHA256SUMS.asc          (optional GPG signature)
    ├── MANIFEST.txt            license + source attribution for every file
    └── RELEASE-NOTES.md        changes, known issues, tested emulators/hardware
```

`dist/` holds only final, checksummed release artifacts and their metadata.
Intermediate staging trees live under `build/` and are never committed.

## 16.10 Reproducibility and release checklist

**Reproducibility principles.** A given tag must rebuild to byte-identical
artifacts on any Linux host:

- Build from a **clean checkout** at the release tag (`git clean -fdx` before
  building) so no stray files enter an image.
- Compile with **Open Watcom** using pinned flags (`wcl -0 -bt=dos -ml -os`);
  the toolchain version is recorded in `RELEASE-NOTES.md`.
- Fix all sources of nondeterminism in media:
  - `mformat -N 0` — fixed FAT volume serial number.
  - Fixed volume labels (`-v CASTALIA`, `CASTALIA_NN`).
  - `SOURCE_DATE_EPOCH` exported and `mcopy -m` so file timestamps are
    deterministic; sorted file lists feed `mcopy` and `zip`.
  - A single committed FreeDOS boot sector (`build/boot/fdboot.bin`,
    `fdboot16.bin`) rather than regenerating it per build.
  - `zip -X` (no extra attributes) over a `LC_ALL=C sort`ed file list.
- The whole pipeline is driven by `scripts/` (`build.sh`, `mkfloppy.sh`,
  `mkzip.sh`, `mkiso.sh`, `mkcf.sh`) plus `wmake`, so a release is one command.

**Release checklist** (all must pass before tagging):

| # | Gate | How |
|---|---|---|
| 1 | Clean build | `git clean -fdx`; `wmake clean && wmake`; run `scripts/build.sh` from a fresh checkout |
| 2 | License manifest present | `LICENSES/` complete (MIT, GPLv2, Artistic-1.0, Info-ZIP, CWSDPMI, CC BY 4.0, CC0); `MANIFEST.txt` lists every shipped file's license + source; GPL component sources present in `third_party/` |
| 3 | Legal separation verified | no Microsoft code/binaries/text/branding; Castalia (MIT) and FreeDOS (GPL) kept separate, no static linking of GPL into MIT binaries |
| 4 | Test gate passed | every produced artifact boots and smoke-tests in **DOSBox-X** and **86Box**; `MEM /C` memory targets met per profile; flagship 386SX Edition validated on real hardware for 1.0+ |
| 5 | Checksums generated | `SHA256SUMS` + per-file `.sha256` written; `sha256sum -c SHA256SUMS` clean |
| 6 | Reproducibility spot-check | rebuild on a second host; artifacts are byte-identical (or differences explained and eliminated) |
| 7 | Metadata written | `RELEASE-NOTES.md` (changes, known issues, tested emulators/hardware, toolchain version) present in the release dir |
| 8 | Version strings match | filenames, `CASTALIA.INI`, and `CASTALIA.EXE` about box all report `<version> "<codename>"` |
| 9 | Tag the git release | annotated tag `v<version>-<codename>` on the reviewed commit; push tag; attach `dist/<version>-<codename>/*` to the GitHub release |

Only after gate 9 is a build an official CASTALIA DOS release. Copyright and
licensing follow the project summary: © 2026 The Castalia DOS Project (repo
owner `davabe`); original Castalia code MIT; documentation CC BY 4.0; modified
FreeDOS components remain GPLv2+ and ship with source in `third_party/`.
