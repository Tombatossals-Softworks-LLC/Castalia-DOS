# 5. Boot Process Design

CASTALIA DOS boots the way DOS has always booted — BIOS, boot sector, kernel,
`CONFIG.SYS`, `COMMAND.COM`, `AUTOEXEC.BAT` — but the `CONFIG.SYS` menu and the
`AUTOEXEC.BAT` branching are engineered to give the user a clear choice of
memory profile and to get every tool out of the way before a game runs.

The complete, ready-to-use files live in [`config/`](../config/):

| File | Installed to | Role |
|---|---|---|
| [`config/CONFIG.SYS`](../config/CONFIG.SYS) | `C:\CONFIG.SYS` | boot menu + per-profile driver loading |
| [`config/AUTOEXEC.BAT`](../config/AUTOEXEC.BAT) | `C:\AUTOEXEC.BAT` | environment + per-profile TSRs + menu |
| [`config/CASTALIA.INI`](../config/CASTALIA.INI) | `C:\CASTALIA\CFG\` | tool settings / branding |
| [`config/PROFILES.INI`](../config/PROFILES.INI) | `C:\CASTALIA\CFG\` | profile descriptions |
| [`config/GAMES.INI`](../config/GAMES.INI) | `C:\CASTALIA\CFG\` | game database |
| [`config/GAMES.BAT`](../config/GAMES.BAT) | `C:\CASTALIA\BIN\` | launcher handoff wrapper |
| [`config/SOUND.BAT`](../config/SOUND.BAT) | `C:\CASTALIA\CFG\` | sound environment (generated by SETSOUND) |

These files are the answer to Section 18 (production first-draft
`CONFIG.SYS`/`AUTOEXEC.BAT`) as well — they are complete and usable.

## Boot targets

CASTALIA DOS boots from three kinds of media, all using the FreeDOS boot
sector and `KERNEL.SYS`:

1. **3.5″ floppy** — a self-contained boot/rescue disk (1.44 MB). Also the
   installer's first disk.
2. **Hard drive** — a FAT16 partition marked active; the normal way the
   system runs.
3. **CompactFlash / IDE** — identical to hard-drive boot; CF appears to the
   BIOS as an IDE disk. The installer validates CF geometry.

## Boot from floppy

The boot floppy carries a minimal but functional system:

```
A:\ KERNEL.SYS  COMMAND.COM  CONFIG.SYS  AUTOEXEC.BAT
    \DOS\   HIMEMX.EXE  JEMM386.EXE  MEM.EXE  FDISK.EXE
            FORMAT.EXE  SYS.COM  CHKDSK.EXE  EDIT
    \CASTALIA\BIN\  HWINFO.EXE  SAFEBOOT.EXE  CFGEDIT.EXE  SETUP.EXE
```

Booting the floppy gives you the Castalia boot menu (a reduced set of profiles
on the rescue disk) and, from `AUTOEXEC.BAT`, the choice to run **SETUP** to
install to a hard disk, or to drop to a prompt for manual repair.

## Install from floppy to hard drive

The floppy's `SETUP.EXE` performs the full install (see
[`INSTALL.md`](INSTALL.md)). In short:

```
Boot A:  ─►  Castalia menu  ─►  "Install / Setup"  ─►  SETUP.EXE
   1. Detect / partition / format the target (FAT16)
   2. SYS the target so it boots            (writes boot sector + kernel)
   3. Copy C:\DOS, C:\CASTALIA, config files
   4. Back up any existing CONFIG.SYS / AUTOEXEC.BAT first
   5. Offer to build an emergency boot disk
   6. Reboot from the hard disk
```

`SETUP.EXE` never overwrites an existing `CONFIG.SYS`/`AUTOEXEC.BAT` without
first copying them to `C:\CASTALIA\BACKUP`.

## Boot from hard drive / CF

Normal operation. BIOS loads the FreeDOS boot sector from the active FAT16
partition, which loads `KERNEL.SYS`, which reads `C:\CONFIG.SYS` and shows the
Castalia menu. This is the path 99% of sessions take.

## The boot banner — CASTALIA, not FreeDOS

The goal is a gate that opens onto **CASTALIA DOS**. Three things shape the
sign-on:

1. **The FreeCOM banner is blanked.** FreeCOM (`COMMAND.COM`) normally prints
   a "FreeCom version 0.85a - WATCOMC - XMS_Swap [date]" line as it starts.
   [`scripts/rebrand-dos.py`](../../scripts/rebrand-dos.py) blanks that one
   banner format string in the freshly fetched `COMMAND.COM` at build time —
   in place, length-preserving, no logic touched.
2. **The kernel is rebuilt with a CASTALIA sign-on.** The stock FreeDOS 1.3
   kernel prints "FreeDOS kernel 2043 … WATCOMC …" and the Villani/GPL
   copyright, and in that build `signon()` does so *unconditionally* from a
   packed (exeflat + UPX) image — so the banner cannot be byte-patched.
   Instead, [`scripts/build-kernel.sh`](../../scripts/build-kernel.sh)
   rebuilds the kernel from its official source (`ke2043s.zip`) with one
   marked change — [`scripts/patch-kernel-src.py`](../../scripts/patch-kernel-src.py)
   rewrites `signon()` to a single `CASTALIA DOS 386SX Edition` line — and
   ships it **uncompressed**, so the only kernel sign-on is CASTALIA. The CI
   "DOS build" job (which has Open Watcom) runs the rebuild; the resulting
   `build/KERNEL.SYS` replaces the stock kernel in the image. This is a
   GPLv2 source modification: FreeDOS's copyright, licence, and warranty stay
   in the shipped source (`third_party/`), `LICENSES/`, and the Castalia
   **About** screen, and the change is recorded in
   [`LICENSE-STRATEGY.md`](LICENSE-STRATEGY.md) §2.3.2a.
3. **A keep that rises.** Right before the menu, `AUTOEXEC.BAT` runs
   `BANNER.EXE`: the fortress keep rises from the ground, the **CASTALIA DOS**
   wordmark lights up amber, and the tower pennants flicker — then it clears
   out of the way in ~3 seconds (any key skips). The rescue/install floppy
   shows the same keep with a framed command list (`BANNER /R`). Keep art and
   the block-letter wordmark are shared from
   [`src/common/LOGO.C`](../../src/common/LOGO.C).

## The boot menu (`CONFIG.SYS`)

### The syntax this kernel actually has

The FreeDOS kernel does **not** implement the MS-DOS multi-config scheme.
There is no `[MENU]` section, no `MENUITEM`, and no named `[block]` headers:
grep the kernel source for `MENUITEM` and you get nothing, and `kernel/config.c`
has no code that reads `[` at all. It has its own, simpler scheme, and this is
the one Castalia uses:

| Directive | What the kernel does with it |
|---|---|
| `MENUCOLOR=fg,bg` | Clears the screen to that attribute and turns on the highlight bar. Must come **before** the `MENU` lines — the clear homes the cursor, and the bar's row is counted from there. |
| `MENUDEFAULT=n,secs` | Preselects entry *n* and starts a countdown. |
| `MENU <text>` | Prints one line of the menu screen. If the text (after leading spaces and CP437 box-drawing characters) starts with a **digit**, that line becomes selectable entry *n* and the highlight bar covers it. |
| `n?DIRECTIVE` | The directive runs only when entry *n* was chosen. Several digits mean several entries: `345?DEVICE=…` runs for 3, 4 and 5. |
| unprefixed directive | Always runs — this kernel's equivalent of `[COMMON]`. |

The kernel exports the chosen entry as `%CONFIG%`, and **it is the digit**
(`"1"`…`"8"`), not a block name — `config.c` literally does
`sprintf(envp, "CONFIG=%c", MenuSelected+'0')`. `AUTOEXEC.BAT` turns that digit
into the readable profile name everything else branches on.

> This is written out at length because Castalia originally shipped the MS-DOS
> syntax. It looked right, it parsed without complaint, and it was completely
> inert: with no `n?` prefixes anywhere, *every* profile's `DEVICE=` lines ran
> on *every* boot (HimemX and Jemm386 loading six times over), `%CONFIG%` was
> never set, and `GOTO %CONFIG%` died with "No label specified for GOTO". No
> emulator caught it because nobody had booted the *installed* system — only
> the rescue floppy, which has no menu. `scripts/check.sh` now fails the build
> if `[MENU]` or `MENUITEM` reappears in `config/CONFIG.SYS`.

```
MENUCOLOR=7,1
MENUDEFAULT=2,10

MENU
MENU      CASTALIA DOS 386SX Edition   -   choose a boot profile
MENU      ---------------------------------------------------------
MENU
MENU      1. Maximum Compatibility ... HIMEM only, no EMM, no UMB
MENU      2. XMS Gaming .............. HIMEM + UMB, no EMS page frame
MENU      3. EMS Gaming .............. HIMEM + 64 KB EMS frame + UMB
MENU      4. CD-ROM Gaming ........... EMS + CD-ROM driver + sound
MENU      5. Windows 3.x Mode ........ EMS + mouse (+ your SMARTDRV)
MENU      6. Diagnostics ............. boot, then run HWINFO
MENU      7. Safe Mode ............... bare kernel, no drivers
MENU      8. Command Prompt Only ..... no Castalia menu, straight to DOS
MENU

1234568?DEVICE=C:\DOS\HIMEMX.EXE
2?DEVICE=C:\DOS\JEMM386.EXE NOEMS I=B000-B7FF
345?DEVICE=C:\DOS\JEMM386.EXE FRAME=E000 I=B000-B7FF
168?DOS=HIGH
2345?DOS=HIGH,UMB
7?DOS=LOW
4?DEVICE=C:\CASTALIA\DRV\UIDE.SYS /D:CASTLCD1 /N1 /N3
```

Each entry maps to a set of prefixed directives **and** an `AUTOEXEC.BAT`
branch. The eight options and their implementations:

| # | Menu option | `CONFIG.SYS` directives | `AUTOEXEC.BAT` branch does |
|---|---|---|---|
| 1 | Maximum Compatibility | HIMEMX + `DOS=HIGH` | banner → menu, no TSRs |
| 2 | XMS Gaming (default) | +JEMM386 NOEMS +UMB | mouse high → menu |
| 3 | EMS Gaming | +EMS frame +UMB | mouse high → menu |
| 4 | CD-ROM Gaming | +UIDE +UMB | mouse + SHSUCDX high → menu |
| 5 | Windows 3.x Mode | +EMS +UMB | mouse + SMARTDRV if present → menu |
| 6 | Diagnostics | HIMEMX + `DOS=HIGH` | run `HWINFO.EXE` → prompt |
| 7 | Safe Mode | `DOS=LOW`, nothing loaded | rescue banner → prompt |
| 8 | Command Prompt Only | HIMEMX + `DOS=HIGH` | banner → prompt (no menu) |

The full driver lines are in [`config/CONFIG.SYS`](../config/CONFIG.SYS); the
per-profile memory analysis is in [`MEMORY.md`](MEMORY.md).

### Why the CD-ROM driver runs uncached

`UIDE.SYS` defaults to a **20 MB XMS cache**, and its smallest setting is 5 MB.
A 4 MB 386SX has roughly 3 MB of XMS, so the default does not merely perform
badly — it fails outright with `XMS init error; UIDE not loaded!` and the
CD-ROM never appears. `/N3` runs UIDE with no XMS cache at all, and `/N1`
restricts it to CD/DVD drives so it never inserts itself under the hard disks.
`/N3` also refuses to load from upper memory, which is why that one line uses
`DEVICE=` rather than `DEVICEHIGH=`. On a machine with 16 MB or more, `/S:5 /H`
buys a 5 MB cache loaded high instead.

### Priority: maximum conventional memory

`MENUDEFAULT=2,10` makes the memory-efficient XMS profile the default after a
10-second timeout. The unprefixed directives are kept deliberately lean (only
`SHELL`, `FILES`, `BUFFERS`, `LASTDRIVE`, `FCBS`, `STACKS=0,0`) so that even
Safe Mode stays small and every profile starts from a low-overhead base.
`DOS=HIGH` (where a memory manager is present) relocates DOS into the HMA to
free ~45–50 KB.

## `AUTOEXEC.BAT` branching

`AUTOEXEC.BAT` first turns the menu digit into a profile name, then runs a
shared prologue, then branches on the name:

```
@ECHO OFF
SET CASTPROFILE=
IF "%CONFIG%"=="1" SET CASTPROFILE=CLEAN
IF "%CONFIG%"=="2" SET CASTPROFILE=XMS
...
IF "%CONFIG%"=="8" SET CASTPROFILE=PROMPT
IF "%CASTPROFILE%"=="" SET CASTPROFILE=CLEAN

SET CASTALIA=C:\CASTALIA
SET PATH=C:\CASTALIA\BIN;C:\DOS;C:\
SET TEMP=C:\TEMP
...
PROMPT [CASTALIA $P]$G
IF "%CASTPROFILE%"=="SAFE" GOTO SAFE
IF EXIST C:\DOS\KEYB.EXE   C:\DOS\KEYB.EXE US,,C:\DOS\KEYBOARD.SYS
IF EXIST C:\CASTALIA\CFG\SOUND.BAT CALL C:\CASTALIA\CFG\SOUND.BAT
GOTO %CASTPROFILE%

:XMS
IF EXIST C:\CASTALIA\DRV\CTMOUSE.EXE LH C:\CASTALIA\DRV\CTMOUSE.EXE
GOTO BANNER
...
```

`%CASTPROFILE%` is the variable every Castalia tool already reads, so deriving
it here keeps one name in play. The final `IF "%CASTPROFILE%"==""` covers the
cases where the menu never ran — `F5` skipped `CONFIG.SYS`, or someone edited
the menu out.

The complete, commented file is [`config/AUTOEXEC.BAT`](../config/AUTOEXEC.BAT).
Three design points matter:

- **Graceful degradation.** Every optional driver load is guarded with
  `IF EXIST`, so a build that omits (say) the CD driver still boots cleanly.
- **No redirection characters in a `REM`.** FreeCOM scans a line for `>`, `<`
  and `|` *before* it notices the line is a comment, so a comment that merely
  draws an arrow makes the shell try to redirect into a file. Castalia shipped
  a comment reading `[CASTALIA C:\>]` and every boot answered
  `Can not redirect output to file ']'`. `scripts/check.sh` now greps every
  shipped `.BAT` for it.
- **Plain-ASCII prompt.** No profile loads an ANSI driver, so colour escapes
  in `PROMPT` print as literal `←[1;33m` garbage rather than colour. The prompt
  is `[CASTALIA $P]$G`.
- **The menu loop and batch handoff.** For game profiles, `AUTOEXEC.BAT` enters
  a loop that runs `CASTALIA.EXE`; when the user chooses "Launch Games,"
  `CASTALIA.EXE` exits with errorlevel 10, the loop runs `GAMES.BAT`, which
  runs `LAUNCH.EXE`, which writes `_RUNGAME.BAT` and exits with errorlevel 77 —
  so both menu programs are **out of memory** when the game runs. See
  [`LAUNCHER.md`](LAUNCHER.md).

## Emergency safe mode

Safe Mode is a first-class boot option (menu item 7), not a hidden key combo.
It loads nothing, keeps DOS low, and lands at a prompt with a banner that
points at the repair tools. Because it needs no drivers, it boots even when a
profile edit or a driver is what broke the machine.

## Recovery boot disk

The installer offers to create an **emergency boot disk** — the same
self-contained floppy described under "Boot from floppy," carrying the rescue
tools (`SAFEBOOT`, `CFGEDIT`, `HWINFO`, `FDISK`, `FORMAT`, `SYS`). If the hard
disk ever fails to boot, this floppy boots the machine, and `SAFEBOOT.EXE` can
restore a known-good `CONFIG.SYS`/`AUTOEXEC.BAT` from `C:\CASTALIA\BACKUP` or
re-`SYS` the hard disk.

## Boot flow diagram

```
BIOS POST
   │
   ▼
Boot sector (floppy A: or active HDD/CF C:)
   │  loads KERNEL.SYS
   ▼
CONFIG.SYS  ──►  MENU lines  ──►  user picks 1..8  ──►  %CONFIG% = "1".."8"
   │  run only the "n?" directives for that digit
   ▼
COMMAND.COM  ──►  AUTOEXEC.BAT
   │  digit ──► %CASTPROFILE%, then shared env + sound + keyboard
   ▼
GOTO %CASTPROFILE%
   ├─ CLEAN/XMS/EMS/CDROM/WIN3X ─► TSRs ─► CASTALIA.EXE menu loop
   ├─ DIAG   ─► HWINFO.EXE ─► prompt
   ├─ PROMPT ─► prompt (no menu)
   └─ SAFE   ─► rescue banner ─► prompt
```

This is the whole boot contract: a faithful DOS boot, a clear profile choice
that defaults to maximum conventional memory, and a menu that always unloads
before a game runs.
